# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

A personal knowledge base of reference documents about the Line 6/Yamaha **Helix / HX** guitar
multi-effects processor family (converted from PDF to Markdown), plus `src/`, which now holds
original tooling built on top of that knowledge and a folder of vendored community projects used
as reference while building it. The repo itself has no top-level build system — each project under
`src/` is self-contained with its own build/test setup.

## Layout

- `pdf/` — original source PDFs (the authoritative originals).
- Top-level `.md` files — Markdown conversions of each PDF, same base filename. These are OCR/layout-converted, so tables, columns, and headers can be jumbled or out of visual order relative to the original PDF; when precise wording or layout matters, cross-check against the corresponding file in `pdf/`.
- `src/hxcli/` — `hx-cli`: a Python CLI + MCP server (`hx_mcp/`) for reading/inspecting/safely editing standalone `.hlx` preset files. MIT, clean-room (own byte-exact JSON codec — see its README for why that matters). Has its own test suite (`pytest`).
- `src/hxviewer/` — `hx viewer`: a Next.js/TypeScript app that renders a `.hlx` preset as a signal-chain view (blocks, params, snapshots) entirely client-side. MIT. Ships no Line 6 artwork/model catalog, but `npm run import-res` pulls names/icons/units from a local HX Edit install into gitignored `public/hx-res/` — see its README.
- `src/vendor/` — community Helix/HX tooling cloned in **for reference only**, not depended on by `hxcli`/`hxviewer`: `openhx`, `helaix`, `phelix` (GPL-3 — do not copy its code or data into the MIT projects above), `HelixBackupFiles`, `helix-stadium-mcp` (targets a different, newer product line — see below), `fretwire`, `hxlinux`, `openpodgo`.

Current manual/guide documents:
- `Helix LT 3.80 Owner's Manual - English.md` + `Helix LT Cheat Sheet - English.md` — **the user's own device.** Prefer these over the Floor equivalents for anything hardware-specific (panel, footswitches, views).
- `Helix 3.80 Owner's Manual - English.md` + `Helix Cheat Sheet - English.md` — the **Floor** equivalents. Same firmware (v3.80) and identical for signal-path/effects material, but the panels differ (see below). Each manual has a table of contents near the top mapping topics to PDF page numbers.
- `HX Edit Pilots Guide 3.80 - English.md` — the official HX Edit editor/librarian guide (~298KB); the reference for what the desktop editor does, which is what `hxviewer` mimics.
- `8c45ddd-...-HELIX_HX_Tone_Secrets_PDF_Lead_Magnet.md` — a third-party ("Hey Worship Leader") guide with opinionated tone/preset-building tips for worship-style guitar rigs, written for firmware 3.60+.

**Floor vs LT differences that matter** (both confirmed in the LT docs): the LT has **no per-switch scribble strips** — footswitch labels live on the main display via **Home > Performance view**, which shows the middle eight assignments 4-across by 2-down; and the LT's Stomp mode is always "the middle eight footswitches", with no Floor-style 10-switch option. Both devices share the same **FS1–FS12** grid (two rows of six: FS1/FS7 = BANK up/down, FS6 = Preset/Stomp mode, FS12 = TAP/tuner, middle eight = FS2–5 and FS8–11).

## Working with the manuals

- When answering questions about Helix/HX features, settings, or terminology, treat the Owner's Manual as authoritative over the informal/opinionated third-party guide — and prefer the **LT** manual, since that's the user's hardware.
- Since the `.md` conversions can have OCR artifacts (misplaced table cells, merged headings, stray characters), verify important details against the source PDF in `pdf/` before treating a surprising claim as fact.
- If new manuals or guides are added, follow the existing convention: keep the source PDF in `pdf/` and add a Markdown conversion at the repo root with a matching filename.

## Working on the code projects

- The user's own hardware is a **Helix LT**. `phelix` in `src/vendor/` was explicitly tested against a Helix LT on firmware 3.80 and is the most trustworthy format reference among the vendored repos when in doubt.
- **`.hlx`** (single preset export/import, what HX Edit and the hardware both read) is plain JSON, but formatted oddly: `"key" : value` (space before colon), floats printed at full `%.17g` precision rather than shortest round-trip, lowercase `true`/`false`. A stock JSON library round-trips it but silently reformats it. `hx_cli/codec.py` reproduces the exact byte layout, and `hxviewer/lib/hlx/codec.ts` is a TS port of it (needed there too, since the viewer now exports edited presets). The TS side additionally needs `lib/hlx/parse.ts`: JS hoists integer-like object keys, so plain `JSON.parse` reorders things like a preset's `irUuidTable` and would reshuffle the file on export.
- **`.hxb`** (full device backup) is a different, real binary container (`"AF6L"` header, zlib-deflated sections, footer offset table) — harder to edit safely than a standalone `.hlx`. Nothing in this repo edits `.hxb` yet.
- **Licensing discipline matters here**: `hx-cli` and `hx viewer` are both MIT and deliberately clean-room — built by reading vendored projects (and real preset files) to learn *facts* about the format, never by copying their code or bundled data. `phelix` is GPL-3; treat anything learned from it as fact-only, not copyable. Neither project bundles Line 6 artwork, official model names, or a curated parameter catalog, matching the pattern already established by `fretwire` and `openpodgo` (both ship neutral placeholders and let the user import their own already-licensed HX Edit resources locally instead).
- The user has **HX Edit installed at `C:\Program Files (x86)\Line6\HX Edit`**, whose `res/` folder holds the authoritative model data: `HX_ModelCatalog.json` (names, icon filenames, category names/colors), `*.models` (per-model param order, display types, ranges, DSP cost), `HelixControls.json` (value formatting — scales, printf formats, units, and the literal tables behind discrete controls like mic/note-division), plus `icons_models/` and `icons_category/` artwork. `hxviewer`'s `npm run import-res` reads these into gitignored `public/hx-res/`. **Never commit that output or copy those assets into the repo** — they're proprietary; the whole design keeps them on the user's machine only.
- **`.hlx` routing model** (derived empirically from the 24 phelix presets / 48 DSP paths; encoded in `hxviewer/lib/hlx/restructure.ts`): `@position` is a slot index *within a path branch*, not a global one — two blocks share a position when their `@path` differs (0 = upper branch A, 1 = lower branch B), and `(@path, @position)` was unique in every path checked. Reordering must therefore *exchange* `@position` between two blocks on the same branch, never renumber, or split/join routing breaks. `@type` tracks the catalog category (FX = 0, Amp = 3 when it has a `@cab` / 1 when not, Cab = 2, IR = 5, Looper = 6, Delay & Reverb = 7), and structural keys are category-specific: `@trails` only on Delay/Reverb, `@bypassvolume`/`@cab` only on Amp, and Amp blocks carry no `@stereo` (amps are mono). That last point is why model swapping is restricted to within a category — a cross-category swap would have to synthesize or drop those keys.
- **Hardware-view layout** (`hxviewer/lib/hlx/grid.ts`): the Helix Home screen draws each path as a slot grid — `@path` picks the row (0 = upper A, 1 = lower B), `@position` picks the column; split/merge carry a position but no `@path` (they sit on the spine); inputs/outputs carry neither and pin to the ends; an amp and the cab it names via `@cab` are drawn as one Amp+Cab slot. Two footswitch fields are **not** trustworthy and are deliberately not relied on: `@fs_ledcolor` decodes to implausible near-black values in several real presets (the view uses the block's category colour instead, which is Helix's own default), and `@fs_index` ranges 2..18, so it cannot be a switch number and is used only for ordering — the index-to-physical-switch mapping is undecoded (fretwire's docs note the same). The panel's 12-switch grid (FS1-FS6 over FS7-FS12; FS1/FS7 = BANK up/down, FS6 = Preset/Stomp mode, FS12 = TAP/tuner, middle eight = blocks or snapshots 1-8) is confirmed by the **LT Cheat Sheet**, so it is correct for the user's device; the LCD's `VIEW` button mirrors the LT's toggle between Home > Signal Flow and Home > Performance.
- `hxviewer`'s `HardwareView`/`FootswitchPanel` deliberately do **not** `useMemo` on `preset`: edits mutate the preset tree in place so its object identity never changes, and a `[preset]` dependency serves stale layout/snapshot state after every edit (this bit once — the panel kept showing the old active snapshot).
- **Snapshots are stored twice and must not drift**: `tone.global.@current_snapshot` names the active one; `tone.snapshotN.blocks[dsp][slot]` holds per-snapshot bypass and `tone.snapshotN.controllers[...]["@value"]` holds per-snapshot values for parameters assigned to the Snapshots controller; the block's own `@enabled` and parameter values mirror the *active* snapshot (verified: 203 bypass entries + 53 controller params across 24 presets, zero mismatches). Any edit to bypass or a snapshot-controlled parameter must write **both** places, or the hardware silently reverts it on the next snapshot recall — `hxviewer/lib/hlx/snapshots.ts` does this. Note `controllers` has two container shapes: DSP paths nest `block -> param -> entry`, device containers like `variax` hold params directly, so detect the level from the value, not the key. Snapshot `@tempo` does *not* mirror `global.@tempo` — leave it alone.
- Two non-obvious traps in that data, both already handled in `scripts/import-res.mjs` — preserve the fixes if you touch it: (1) a model id can appear twice in the catalog (a Mono entry holding the artwork plus a Stereo entry with `"image": "None"`), so entries must be *merged*, not overwritten, or ~150 models silently lose their icons; (2) `@`-prefixed params are a mix — those with a `displayType` are real user-facing controls (`@mic`, `@trails`, `@bypassvolume`), those without are structural (`@enabled`, `@stereo`, `@cursor_*`), so filter on `displayType`, not on the `@` prefix.
- `helix-stadium-mcp` in `src/vendor/` is kept only as a design reference (its MCP tool-surface + validate→round-trip→backup safety-gate pattern was worth reusing) — it targets **Helix Stadium**, a separate, newer Line 6 product line with its own `.hsp` format, not the classic Helix Floor/LT/Rack/HX Stomp family this repo's tools are for.
